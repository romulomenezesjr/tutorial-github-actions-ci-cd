03

Em aula 7 min

Seu primeiro workflow

Entenda

Todo arquivo YAML dentro de .github/workflows/ é um workflow. Este tem quatro partes:

  • name: o nome que aparece na aba Actions.
  • on: os gatilhos. Aqui, todo push na main e todo pull request.
  • jobs.testes: um job que roda numa máquina virtual Ubuntu nova a cada execução.
  • steps: os passos, em ordem. uses executa uma action pronta; run executa um comando no shell.

Entenda

08

Desafio intermediário 20 min

Formatação com Prettier

Entenda

ESLint e Prettier se complementam, e cada um cuida de uma coisa:

FerramentaCuida deExemplos
ESLintQualidade: código que provavelmente tem bugvariável nunca usada, == no lugar de ===, var
PrettierAparência: como o código é escrito na telaespaços, aspas, ponto e vírgula, quebras de linha

O Prettier não discute estilo: ele reescreve o arquivo sempre do mesmo jeito. Com a configuração no repositório, todo mundo da equipe formata igual, e o code review fica livre de comentários sobre espaços e aspas. No CI, prettier --check falha se algum arquivo não estiver formatado.

O pacote eslint-config-prettier desliga as regras de estilo do ESLint que poderiam brigar com o Prettier. Assim, cada ferramenta fica só com o seu papel.

Sugestão de configuração do Prettier

Algumas opções abaixo já são o padrão do Prettier. Elas ficam escritas no arquivo para documentar a decisão da equipe.

OpçãoValorO que faz
semitruePonto e vírgula no fim de cada instrução. É o padrão.
singleQuotetrueAspas simples em JavaScript. O padrão do Prettier é aspas duplas.
trailingComma"all"Vírgula depois do último item de listas e objetos quebrados em várias linhas: acrescentar um item muda uma linha só no diff. É o padrão.
printWidth100Largura máxima da linha. O padrão é 80, apertado para telas atuais.
tabWidth2Dois espaços por nível de indentação. É o padrão.
endOfLine"lf"Quebra de linha no estilo Linux, mesmo para quem usa Windows. Evita diffs em que todas as linhas parecem alteradas. É o padrão.

Sugestão de regras para o ESLint

As regras recomendadas do ESLint são um bom começo. Estas cinco acrescentam boas práticas que costumam pegar erros de iniciante:

RegraO que exigePor quê
eqeqeq=== e !==O == converte tipos antes de comparar: 0 == '' dá true.
no-varlet ou constvar vale para a função inteira, não só para o bloco, e causa bugs difíceis de achar.
prefer-constconst quando o valor não mudaQuem lê sabe na hora o que pode mudar e o que não pode.
no-consoleAviso para console.logLembra de tirar os logs de depuração. Por ser aviso (warn), não falha o CI.
no-unused-varsNenhuma variável sobrando, exceto parâmetros que começam com _Permite marcar de propósito um parâmetro que a função recebe mas não usa.

Proteger a main

Entenda

Até aqui, nada impedia um push direto na main com testes quebrados. Um ruleset obriga que toda mudança na main chegue por pull request e só entre com os checks verdes. Depois desta seção, todas as alterações passam pelo ciclo de PR.

Atividade 9

Criar o ruleset e testar

  4. Em Branch rules, mantenha Restrict deletions e Block force pushes marcados, e marque também:

Segredos e variáveis

Entenda

Senhas e tokens nunca vão no código. O GitHub guarda secrets criptografados e os entrega ao workflow na hora da execução; se algum aparecer no log, é trocado por ***. Para configurações que não são sigilosas, como o nome de um ambiente, use variables. O gatilho workflow_dispatch cria um botão para rodar o workflow manualmente.

Atenção

O mascaramento é uma rede de segurança, não uma garantia: se o segredo for transformado (codificado em base64, por exemplo), a versão transformada aparece no log. Nunca imprima segredos de propósito. Segredos também não são entregues a workflows disparados por PRs vindos de forks.

Dica

Repare que o segredo e a variável chegam ao shell por env:, e não escritos direto dentro do run:. Esse é o jeito seguro de passar qualquer valor externo para um comando: evita que o conteúdo seja interpretado como código (injeção).

12

Extra 15 min

Endurecer o pipeline

Entenda

Quatro ajustes que todo pipeline de produção deveria ter:

  • permissions: contents: read: o token do workflow só pode ler o repositório (menor privilégio).
  • concurrency: um push novo cancela a execução anterior da mesma branch, que já ficou obsoleta.
  • timeout-minutes: o padrão é 6 horas. Um job travado gastaria cota à toa.
  • Dependabot: abre PRs sozinho quando sai versão nova de uma action ou de uma dependência do npm.

De bônus, fail-fast: false deixa as outras combinações da matriz terminarem mesmo se uma falhar, para você ver o quadro completo.

Por que fixar pelo SHA?

Em março de 2025, as tags da action tj-actions/changed-files, usada em mais de 23 mil repositórios, foram redirecionadas para um código malicioso que imprimia segredos nos logs. Quem usava o SHA fixo não foi afetado.
